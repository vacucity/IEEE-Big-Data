## 1. 直接重建提交文件

解压交接包后，在包含本说明的目录运行。使用 Python 3.10 或更高版本即可，脚本只用标准库。

```sh
python rebuild_v85.py
```

脚本读取保存的 80 窗口审计和 12 个候选格子的证据，重新判断门槛，再按 `(split, panel, window_id, link_id, timestamp)` 与 `inputs/v84_queue.csv` 对接。目标时间为 `date` 当日 UTC 零时加 `5*T + horizon_minutes`。脚本重新得到 10 个 `submission_id`，与正式改动清单核对，然后从 V84 写出 `reproduced/V85_history_guard_rebuilt.zip`。

校验会读取全部 6,980,503 条数据行，检查重建出的 `submission.csv` 与正式 V85 **逐字节一致**。重新压缩后的 ZIP 容器受元数据和压缩库版本影响，复现验收以内部 CSV 字节为准。原始提交包与校验值见下表。

## 2. 从冻结概率重算候选格子

这一步从预处理数据和已缓存的 CPU 模型概率重跑历史检索与门槛，得到候选审计，然后再重建提交。交接包含 24 份正式窗口概率缓存和 8 份训练期相邻排队共现表。队友需要已有 V84 工程产出的 `clean_data/` 和赛事解压后的 `kaggle_public/`。前者须含 `cleaning_report.json` 和八个 Task 2 面板的 `links/train/validation/private.parquet`。后者须含 `config/corridors.json` 和相应的 `task2/<panel>/<split>/window_index.csv`。

本地已用 Python 3.13.9、NumPy 2.3.5、pandas 2.3.3、PyArrow 23.0.0 在 CPU 上通过。按实际路径替换下面两个目录。

```sh
python -m pip install numpy==2.3.5 pandas==2.3.3 pyarrow==23.0.0
python replay_gate_from_cache.py --clean-data "path/to/clean_data" --release "path/to/kaggle_public" --output rerun_gate
python rebuild_v85.py --audit-dir rerun_gate --output reproduced/V85_from_replay.zip
```

`rerun_gate/comparison.json` 对比重算与原始审计，忽略文本行尾差异。两份 CSV 和汇总 JSON 在本次核验中全部一致。第一次运行请使用尚未存在的输出路径。从头生成 V84 与 CPU 概率缓存需要团队的完整工程及模型权重。包内 `reference/v85_cpu_neural.py` 和 `reference/v85_cpu_gbm.py` 是产生这些缓存的历史入口，供队友结合原工程追溯。

## 3. 复现文档可以这样写

1. **窗口范围。** 处理八个面板的正式持续排队窗口。validation 与 private 每个面板各 5 窗，共 80 窗。门槛仅用于 `constr` 窗口，跳过 `D7_I210_E` 的既有傍晚消散规则和条件采样接受率低于 2% 的情况。
2. **历史检索。** 从目标时点 `T` 及之前的 12 个五分钟步长提取历史形状。每个面板最多 16 个空间分箱，每箱使用归一化速度、排队比例与有效观测覆盖率。用三段四步平均构造特征，在 2031-03-01 前的训练历史中，按时钟时间 `±60` 分钟范围和特征均方距离取 30 个最相似起点。30 个起点可以来自重复日期。
3. **概率与门槛。** 在 `constr` 窗口中，根据训练期排队共现分组做 20,000 次条件采样，使用窗口 ID 的 CRC32 作种子，取接受样本均值为 `q_cpu`。对相似历史的未来 5 至 30 分钟，按可用速度与路段阈值统计逐格有效观测数 `n_valid` 和排队比例 `q_hist`。将 `0.9*q_cpu + 0.1*q_hist` 与 `q_cpu` 分别解码，把二者的差异作用于 CPU 重放，并固定首个预测步。只保留 CPU 重放建议 `0→1`、原 V84 同格也为 `0`、`n_valid ≥ 20` 且 `q_hist − q_cpu ≥ 0.30` 的位置。最后在 V84 CSV 中仅更新这些位置的 `queue_pred`。
4. **正式应用。** 门槛前 12 个候选，门槛后 10 个。实际修改涉及的 6 个窗口均未发现原 V84 与 CPU 基线重放不一致。历史案例的未来观测来自已过去的训练数据，目标窗口的检索输入截至 `T`。

本地 March 251 个探索窗口的面板等权代理 IoU，相对 CPU 重放基线为 `+0.000676`，按日聚类的 95% 区间为 `[-0.000324, +0.001747]`。相对无证据门槛的历史规则，仅增加 `+0.000027`，另 11 个同月窗口分数无变化。该窗口集被多次用于筛选，区间包含 0。复现文档应分别报告本地代理实验、提交文件复现与公榜观察结果。
